in-memory package result produced by package orchestration.

- dev-only;
- dry-run-only;
- in-memory-only;

## 14. Status Semantics

A future review may use only non-authorizing review statuses such as:

- `REVIEW_PASS`;
- `REVIEW_BLOCKED`;
- `REVIEW_NEEDS_REVISION`.

Conceptual semantics:

- `REVIEW_PASS` means only that the in-memory package result appears complete,
  consistent, and boundary-safe within the review dimensions;
- `REVIEW_BLOCKED` means the package result contains a boundary violation,
  missing required evidence, unsafe signal, package coverage failure, or
  forbidden surface;
- `REVIEW_NEEDS_REVISION` means the package result is still no-write but needs
  documentary or in-memory package-result revision before a later review.

`REVIEW_PASS` does not authorize:

- implementation;
- real materialization;
- real Target read;
- real Target write;
- renderer;
- writer;
- loader;
- scenario selector;
- Target Adapter;
- Write Approval;
- output persistence;
- generated output;
- materialized output;
- GitHub;
- productive skill access;
- productive skill mutation;
- Aggregator change;
- checker creation;
- tenth check.

The review status vocabulary must avoid positive real-write vocabulary such as:

- `APPROVED`;
- `WRITE_APPROVED`;
- `APPROVAL_GRANTED`;
- `READY_TO_WRITE`;
- `WRITE_UNLOCKED`;
- `EXECUTION_APPROVED`;
- `MERGE_APPROVED`.

If those terms appear in reviewed input as write-enabling status or semantics,
the future review must reject them as positive write vocabulary signals.
