## 18. Support layer responsibility model

The support layer is a conceptual auxiliary architecture serving the canonical
matrix. Its responsibility model separates:

- `_shared`: reusable common rules and common support;
- per-agent support: support specific to one canonical agent's responsibilities;
- activation: minimal and progressive selection of relevant support;
- temperature shards: conceptual organization by expected loading relevance;
- `trace`: audit-only conceptual traceability support;
- `START.md` and `MANIFEST.md`: conceptual entry and activation controls.

These responsibilities describe boundaries, not files, templates, final paths,
runtime behavior, or a physical inventory.

## 19. `_shared` conceptual boundary

`_shared` is conceptually reserved for common rules and support that are
genuinely reusable across canonical agents. It is not an agent, an entrypoint,
a third matrix, a source mirror, or a dumping ground. Commonality must be
established qualitatively; speculative consolidation and whole-source copying
are forbidden. No final `_shared` file, path, inventory, template, placeholder,
or schema is decided here.

## 20. Per-agent support conceptual boundary

Per-agent support is conceptually reserved for project-prepared support that is
specific to one canonical agent's role and cannot be represented correctly as
common support. It supplements but does not replace that agent's GitHub or
Codex entrypoint. It does not create an additional agent count or platform
matrix. No final per-agent support path, file set, shard inventory, template,
placeholder, or body is decided here.

## 21. Activation conceptual boundary

Activation is conceptually reserved for minimal and progressive selection of
support needed for the current responsibility and context. It is a boundary
against eager loading and bloat, not a runtime implementation decision. This
phase defines no algorithm, command, parser, manifest schema, Target adapter,
loading rule, CLI behavior, or executable activation mechanism.

## 22. Temperature shards conceptual boundary

Temperature shards remain conceptual organizational classes:

- `always`: support expected at minimal entry;
- `hot`: support with high contextual relevance;
- `warm`: support loaded for a narrower recurring need;
- `cold`: support loaded only for specific, less frequent needs;
- `trace`: audit-only conceptual traceability support.

These descriptions are qualitative organization boundaries only. They do not
define final content, files, names, paths, quantities, budgets, thresholds,
loading behavior, template families, or inventories.

## 23. Trace relationship boundary

`trace` relates to the support layer only as conceptual auditability support.
It remains audit-only, conceptual-only, non-mirror, and
non-materialization-authorizing. It must not reproduce source bodies, kernels,
Senior Agent Profiles, `/docs`, full shards, or full support packs. This phase
does not define final trace structure, path, inventory, schema, report,
template, placeholder, renderer, checker, validator, metric, or enforcement.

## 24. START and MANIFEST relationship boundary

`START.md` remains the conceptual minimal entry control, and `MANIFEST.md`
remains the conceptual activation control. Their relationship supports small
entrypoints and progressive access to support. The names express inherited
conceptual control roles only; this phase creates neither artifact and does not
define final locations, bodies, formats, schemas, parsing, runtime behavior,
or template inventory for them.

## 25. No third agent matrix boundary

`.sentinel/agents/**` support does not replace conceptual
`.github/agents/**` or `.codex/agents/**` agent artifacts. `_shared`, per-agent

canonical `12/24/2` count.

## 30. No-copy source material boundary

Kernels and Senior Agent Profiles remain strong sources, not literal payloads.
`/docs` remains an on-demand source, not a copied corpus. Whole kernels, whole

complete trace, source mirrors, and `/docs` dumps are forbidden. Future shards
must be project-prepared and traceable rather than literal copies, but this
phase creates no shard or trace artifact.

## 31. Anti-bloat qualitative boundary

The support layer must remain qualitatively lean:

- keep entrypoints small;
- centralize only genuinely common support;
- keep agent-specific support narrowly scoped;
- activate progressively and on demand;
- avoid source duplication, mirrors, broad dumps, speculative content, and
  redundant support;
- use traceability instead of payload duplication;
- preserve clear responsibility separation.

These are qualitative rules only. No numeric threshold, budget, count, metric,
validator, checker, measurement tool, or enforcement is defined or authorized.
