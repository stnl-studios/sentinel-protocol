# coder-frontend Senior Profile Excellent Pass Expectations

Future audit target:

`coder-frontend Senior Agent Profile: EXCELLENT PASS`

Senior profile audit target:

`SENIOR_AGENT_PROFILE_AUDIT: EXCELLENT PASS`

## Structural Excellence

- The module contains exactly the requested profile files under
  `coder_frontend_profile`.
- Required profile sections are present and substantive.
- Validation files are local to the module.
- No global contracts are created by this module.
- The one-of-12 statement is present and explicitly not a partial pilot.

## Kernel Preservation Excellence

- Critical `coder_frontend_kernel` anchors are preserved: executor role,
  `targeted-local` reading, `EXECUTION PACKAGE`, `WORK_PACKAGE_ID`,
  `OWNED_PATHS`, `DO_NOT_TOUCH`, `DEPENDS_ON`, `BLOCK_IF`, front-end quality
  guardrail, evidence, `READY`/`BLOCKED`, and anti-role-drift.
- Kernel content is distilled into operational judgment, not copied.
- The kernel remains the audit and semantic-preservation source.

## Role Boundary Excellence

- The canonical `coder-frontend` role is preserved as front-end executor for
  authorized web/browser UI packages.
- The profile does not expand authority beyond package-bound front-end
  implementation.
- Product, UX, design, backend, API, schema, auth, permission, persistence,
  iOS, package design, validation, review, finalization, and resync decisions
  remain outside `coder-frontend` authority unless already supplied by valid
  upstream source.

## Frontend Execution Excellence

- Heuristics are specific to components, views, client state, routing UI,
  forms, browser interactions, styling, design-system use, accessibility,
  responsive behavior, UI contracts, and local integration.
- The profile implements smallest correct package-bound changes and blocks
  instead of inventing missing upstream decisions.
- Front-end execution stays low-token, bounded, and auditable.

## Execution Package Boundary Excellence

- `EXECUTION PACKAGE` and `WORK_PACKAGE_ID` are required before execution.
- Package fields are consumed as binding constraints, not edited or
  reinterpreted.
- `RUN_COMMANDS`, `ACCEPTANCE_CHECKS`, constraints, dependencies, and blockers
  shape evidence and handoff without turning the coder into package designer.

## Owned Paths / Do-Not-Touch Excellence

- `OWNED_PATHS` define edit authority and are explicit in blocker behavior.
- `DO_NOT_TOUCH` is preserved as a hard boundary.
- Missing, broad, contradictory, or conflicting paths produce exact blockers.

## UI Contract Excellence

- Existing component, state, route, data-flow, design-system, and shared UI
  contracts are preserved when they are part of the authorized slice.
- API and backend contracts are consumed only when stabilized by upstream
  source.
- Contract ambiguity is blocked rather than passed to implementation or
  validation.

## Accessibility And Responsive Behavior Excellence

- The profile treats semantic structure, accessible names, labels, focus,
  keyboard behavior, assistive-state communication, disabled/pending states,
  overflow, layout, and breakpoints as implementation quality when affected.
- Accessibility and responsive checks remain inside the package and do not
  become broad redesign.

## Handoff Excellence

- Minimum input and output are explicit.
- Handoffs preserve `WORK_PACKAGE_ID`, relevant package boundaries, changed
  files, implementation delta, commands, evidence, limitations, residual risk,
  blockers, and next owner.
- Handoff to `validation-runner` enables validation without claiming final
  validation, semantic review, closure, or resync.
- Ambiguous decisions are resolved upstream, routed back, or blocked rather
  than exported downstream.

## Evidence Discipline Excellence

- The profile distinguishes applied change, local evidence, not-run checks,
  inspection confidence, proof gaps, final validation, review, and closure.
- "Looks good", absence of visible error, clean command intent, and visual
  confidence do not replace evidence.
- The profile detects when the correct result is limitation or `BLOCKED`
  rather than `READY`.

## Anti-Overreach Excellence

- The `coder-frontend` does not route, plan, design proof, create validation
  pack, create execution package, resolve design/product ownership, implement
  backend, implement iOS, execute validation, review, finalize, resync, or
  materialize runtime artifacts.
- The profile prohibits downstream role takeover and does not turn seniority
  into additional authority.

## Anti-Bloat Excellence

- No long copy-paste from kernel, base agent, `orchestrator_profile`, or
  `planner_profile` exists.
- The profile is not a general project manual.
- The content stays focused on package-bound front-end implementation,
  boundaries, risks, blockers, evidence, reading budget, and handoff.
- Runtime-oriented instructions are absent.

## Scenario Excellence

- Golden scenarios cover valid front-end package execution, missing package,
  path conflicts, backend contract trap, design/product decision trap,
  dependency and `BLOCK_IF`, refactor creep, validation claim trap,
  accessibility/responsive regression, and runtime leakage.
- Each scenario includes scenario, input, expected guidance, excellent signal,
  and failure modes.
- Scenarios are sufficient for future audit without becoming a runtime test
  suite.

## One-of-12 Consistency Excellence

- This profile reuses the approved documentary shape while remaining
  `coder-frontend`-specific.
- It is not treated as a pilot, subset rollout, partial validation strategy, or
  4-to-12 strategy.
- It does not create artificial demand for a subset of agents.
- It does not return Rodada A to active task status.
- It remains compatible with future repetition for the remaining profiles.

## Quality Bar

The profile is excellent only if it has content specific to `coder-frontend`,
avoids generic seniority language, contains no runtime leakage, contains no
long copy-paste, contains no long copy of `orchestrator_profile` or
`planner_profile`, performs no downstream role takeover, performs no
backend/API/schema/auth/persistence takeover, performs no iOS/native takeover,
does not revive Rodada A as an active task, does not treat this module as a
partial pilot, defines boundaries between front-end implementation, planning,
validation design, execution package design, design ownership, backend
implementation, iOS implementation, validation execution, review, finalization,
and resync, defines clear blockers, provides actionable heuristics, defines a
reading budget compatible with front-end execution, preserves package boundary
discipline, gives enough executor handoff detail for `validation-runner`,
provides enough scenario coverage for future audit, and remains compatible with
future repetition for the other profiles.
