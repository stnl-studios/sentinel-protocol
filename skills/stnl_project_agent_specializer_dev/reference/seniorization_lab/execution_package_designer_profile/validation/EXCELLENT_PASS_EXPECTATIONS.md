local audit bar for `execution_package_designer_profile` and do not authorize
runtime loading, materialization, target writes, productive-skill changes,
template changes, or global contract creation.

## Structural Excellence

- The module contains exactly the requested profile files under
  `execution_package_designer_profile`.
- Required profile sections are present and substantive.
- Validation files are local to the module.
- No global contracts are created by this module.
- The fourth-of-12 statement is present and explicitly not a partial pilot.
- No profiles for the other 8 remaining agents are created by this task.

## Kernel Preservation Excellence

- Critical `execution_package_designer_kernel` anchors are preserved: package
  design after planning and validation design, targeted-local reading,
  ephemeral `EXECUTION PACKAGE`, package readiness gates, bounded work packages,
  proof mapping, safe stop, handoff recovery, no broad discovery, and return to
  orchestrator.
- Kernel content is distilled into operational judgment, not copied.
- The kernel remains the audit and semantic-preservation source.
- The profile does not treat kernel `CLEAN_EXCELLENT_PASS` as runtime,
  materialization, target-write, productive-skill, or production-agent
  authorization.

## Role Boundary Excellence

- The canonical `execution-package-designer` role is preserved as package
  designer, package-boundary owner, field-level safety gate, blocker, and
  coder-handoff preparer.
- The profile does not expand authority beyond pre-execution package design.
- Planning, validation design, detailed design, implementation, validation
  execution, review, finalization, resync, runtime materialization, and coder
  coordination remain outside execution-package-designer authority.

## Execution Package Excellence

- `EXECUTION PACKAGE` is described as an ephemeral, current-round package-design
  handoff when applicable.
- The package contains objective, approved scope, owner candidate, work package
  identity, package fields, proof linkage, blockers, forbidden assumptions, and
  next-owner signal.
- The package does not become a durable file, implementation plan, QA report,
  roadmap, broad spec, repo inventory, or runtime prompt.
- Package readiness is not treated as execution approval or implementation
  readiness.

## Package Boundary Excellence

- Package boundary is small, executable, auditable, and tied to the authorized
  cut.
- In-scope work, non-goals, protected surfaces, dependencies, and blockers are
  explicit.
- Oversized or multi-owner work blocks or splits only when source-backed
  boundaries support the split.
- The package never requires coder re-planning, re-architecting, or ownership
  discovery to start.

## Ownership Excellence

- Each work package has one clear owner/coder family candidate when package
  design is ready.
- `OWNED_PATHS` are source-backed, narrow, and safe as edit authority.
- Shared files, contracts, docs, generated assets, adjacent surfaces, and other
  owners are protected through `DO_NOT_TOUCH` when material.
- Ambiguous ownership is a blocker, not coder discretion.

## Dependency Excellence

- `DEPENDS_ON` records real package, artifact, contract, proof, design,
  schema, migration, or owner dependencies.
- Dependency order and parallelization eligibility are facts returned to the
  orchestrator, not final sequencing decisions by the package designer.
- Hidden dependency inversion and unsafe overlap are detected before coder
  entry.

## Safety Gate Excellence

- `BLOCK_IF` is concrete, actionable, and tied to material risks.
- Missing path, command, dependency, proof mapping, ownership, authorization,
  scope, schema, auth, persistence, payload, contract, or product decision
  blocks instead of being passed downstream.
- `DO_NOT_TOUCH`, forbidden assumptions, and early stop behavior prevent scope
  expansion.
- Execution authorization is never inferred from package-shaped text.

## Acceptance Check Excellence

- `ACCEPTANCE_CHECKS` are traceable to `VALIDATION PACK` obligations.
- Required checks and advisory checks remain separated by proof-design source,
  not package-designer preference.
- Commands and checks are real, package-local when available, and source-backed.
- Generic commands, vague manual checks, and validation theater do not become
  package acceptance.

## Coder Handoff Excellence

- Handoff prepares bounded execution by a coder through orchestrator routing.
- Facts, decisions, package fields, forbidden assumptions, blockers, proof
  linkage, and next owner are separated.
- The package is concise enough to be consumed and rich enough to prevent
  critical guessing.
- Handoff never routes directly to coder, coordinates coders, validates, or
  finalizes.

## Evidence Discipline Excellence

- The profile distinguishes source-backed package fields from invented fields,
  real commands from desired commands, verified paths from presumed paths, real
  dependencies from sequencing guesses, package readiness from execution
  approval, and validation expectation from observed validation.
- "The coder can decide later", silence, context volume, stale artifacts, and
  absence of objection do not replace evidence.
- The profile detects when the correct result is block/ask rather than package
  design.

## Anti-Overreach Excellence

- The `execution-package-designer` does not route as orchestrator, replan,
  create or redesign validation pack, decide proof sufficiency, solve design,
  implement, execute commands, execute validation, declare runner verdict,
  review, finalize, resync, or rewrite out-of-scope profiles and kernels.
- The profile prohibits downstream role takeover and does not turn seniority
  into additional authority.

## Anti-Bloat Excellence

- No long copy-paste from kernel, base agent, `orchestrator_profile`,
  `planner_profile`, or `validation_eval_designer_profile` exists.
- The profile is not a general project manual.
- The content stays focused on package boundary, ownership, dependencies,
  safety gates, commands, acceptance checks, blockers, reading budget, and
  coder handoff.
- Runtime-oriented instructions are absent.

## Scenario Excellence

- Golden scenarios cover clear package design, missing validation pack,
  planning/validation conflict, owned-path ambiguity, implementation pressure,
  command invention, acceptance-check invention, missing `DO_NOT_TOUCH`,
  missing `BLOCK_IF`, multi-owner packages, validation-design takeover,
  validation-runner takeover, context bloat, runtime leakage, and downstream
  ambiguity transfer.
- Each scenario includes scenario, input, expected guidance, excellent signal,
  and failure modes.
- Scenarios are sufficient for future audit without becoming a runtime test
  suite or executable harness.

## Fourth-of-12 Consistency Excellence

- This profile reuses the approved documentary shape while remaining

- It is not treated as a pilot, subset rollout, partial validation strategy, or
