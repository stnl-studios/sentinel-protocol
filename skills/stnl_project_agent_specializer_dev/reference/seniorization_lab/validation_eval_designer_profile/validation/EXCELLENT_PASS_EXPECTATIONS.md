# validation-eval-designer Senior Profile Excellent Pass Expectations

These expectations are documentary/dev-only and non-runtime. They define the
local audit bar for `validation_eval_designer_profile` and do not authorize
runtime loading, materialization, target writes, productive-skill changes,
template changes, or global contract creation.

`validation-eval-designer Senior Agent Profile: EXCELLENT PASS`

Senior profile audit target:

`SENIOR_AGENT_PROFILE_AUDIT: EXCELLENT PASS`

## Structural Excellence

- The module contains exactly the requested profile files under
  `validation_eval_designer_profile`.
- Required profile sections are present and substantive.
- Validation files are local to the module.
- No global contracts are created by this module.
- The third-of-12 statement is present and explicitly not a partial pilot.

## Kernel Preservation Excellence

- Critical `validation_eval_designer_kernel` anchors are preserved: proof
  design before execution package design, validation design separate from
  validation execution, ephemeral `VALIDATION PACK`,
  `NEEDS_DEV_DECISION_HARNESS`, anti-theater validation, harness decision gates,
  targeted-local reading, safe stop, and return to orchestrator.
- Kernel content is distilled into operational judgment, not copied.
- The kernel remains the audit and semantic-preservation source.

## Role Boundary Excellence

- The canonical `validation-eval-designer` role is preserved as proof designer,
  harness judge, validation-pack owner, blocker, and package-readiness input
  provider.
- The profile does not expand authority beyond pre-execution validation design.
- Planning, execution package, design resolution, implementation, validation
  execution, review, finalization, resync, and runtime materialization remain
  outside validation-eval-designer authority.

## Validation Design Excellence

- Heuristics are specific to transforming a bounded `EXECUTION BRIEF` into a
  proof strategy.
- Validation design stays low-token, bounded, auditable, and risk-weighted.
- Designed validation is never treated as executed validation or verdict.

## Validation Pack Excellence

- `VALIDATION PACK` is described as an ephemeral, current-round proof-design
  handoff when applicable.
- The pack contains validation objective, scope under validation, proof
  obligations, evidence modes, required checks, advisory checks, harness
  judgment, blockers, DEV decisions, package-readiness inputs, and next owner.
- The pack does not become a durable file, runtime suite, QA report, execution
  package, or runner verdict.

## Proof Obligation Excellence

- Proof obligations are tied to authorized behavior, contract, state, UX,
  invariant, edge case, regression, risk, or guardrail claims.
- Obligations are derived before commands, suites, manual observations, or
  check types are named.
- Required and advisory validation are separated by material proof need.

## Harness Decision Excellence

- Harness trust is assessed before readiness is claimed.
- Missing, fragile, misleading, disputed, or environment-blocked harness is
  visible when material.
- `NEEDS_DEV_DECISION_HARNESS` is used when DEV must choose focused tests,
  explicit partial evidence, or narrowed cut.
- Harness gaps are not hidden behind generic command success.

## Anti-Theater Excellence

- The profile rejects generic build, lint, smoke, or broad test success when it
  does not prove the changed claim.
- Vague manual checks, visual snapshots without scenario/state/action/result,
  adjacent irrelevant tests, and decorative checklists are treated as false
  confidence.
- The future runner can execute the pack without guessing what evidence would
  count.

## Handoff Excellence

- Minimum input and output are explicit.
- Handoffs separate facts, decisions, proof obligations, forbidden assumptions,
  blockers, and next owner.
- Handoff to `execution-package-designer` enables package design without
  creating package mechanics.
- Ambiguous decisions are resolved upstream, routed back, or blocked rather
  than exported downstream.

## Evidence Discipline Excellence

- The profile distinguishes source truth, evidence expectation, observed
  evidence, testability, harness, blocker, DEV decision, and runner verdict.
- "Should work", silence, context volume, command names, and planning
  confidence do not replace proof basis.
- The profile detects when the correct result is block/ask rather than proof
  design.

## Anti-Overreach Excellence

- The `validation-eval-designer` does not route as orchestrator, replan, create
  execution package, solve design, implement, execute validation, declare
  runner verdict, review, finalize, resync, or rewrite out-of-scope profiles and
  kernels.
- The profile prohibits downstream role takeover and does not turn seniority
  into additional authority.

## Anti-Bloat Excellence

- No long copy-paste from kernel, base agent, `orchestrator_profile`, or
  `planner_profile` exists.
- The profile is not a general project manual.
- The content stays focused on proof obligations, evidence expectations,
  harness, blockers, anti-theater behavior, reading budget, and handoff.
- Runtime-oriented instructions are absent.

## Scenario Excellence

- Golden scenarios cover clear validation design, missing brief, harness
  ambiguity, validation theater, validation-runner takeover, execution-package
  takeover, implementation pressure, source-of-truth ambiguity, required versus
  advisory validation, context bloat, runtime leakage, and downstream ambiguity
  transfer.
- Each scenario includes scenario, input, expected guidance, excellent signal,
  and failure modes.
- Scenarios are sufficient for future audit without becoming a runtime test
  suite.
